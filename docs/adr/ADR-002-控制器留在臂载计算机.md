# ADR-002：控制器留在臂载计算机，不由主机（上位机）直连舵机总线

- 背景：现行架构里臂载计算机上跑厂商控制器（marm_code，4 个 systemd 服务自启，F17），经 /dev/ttyS4 @115200 直挂 7 个 FashionStar 总线舵机（J0–J6）；上位机经网线（<ARM_SUBNET>）与臂载计算机通信。P1.1 将重写控制层（草案 §4.1 ①层），重写后的控制器跑在哪里是必须先定的架构决策（§11 已定，本 ADR 固化）。
- 选项（2–4 个，各一行权衡）：
  1. 控制器留在臂载计算机（重写后仍在板上跑）——控制随臂走；缺点是板上资源受限（aarch64、非 RT 内核，F18）。
  2. 上位机直连舵机总线（控制器上移到上位机，经网线或直接接管串口）——算力充裕、开发调试方便；缺点是臂离开上位机就瘫，臂一上狗即作废。
  3. 外挂小型控制板（如树莓派/Jetson 替换臂载计算机）——硬件自由度高；缺点是新增采购、装机与验证周期，且仍要解决与原装线束/接口的适配。
- 决定：重写后的控制器继续留在臂载计算机上运行；上位机及未来任何上位机只通过平台无关接口（Q1 将以 ADR 定义）下发命令、接收反馈，不直接操作 /dev/ttyS4。
- 理由：D1-T 臂后续要部署到机器狗上，控制必须随臂走，不能依赖上位机这台上位机（§11 卷首、§00.6 第 3 条）；臂 ↔ 上位机接口因此必须与平台无关（换狗载计算机时无需改臂载代码）。
- 后果：
  - 臂载计算机的板卡/内核约束进入设计输入：aarch64、Ubuntu 20.04.6、内核 4.9.113 PREEMPT 非 RT、板上可本地编译 C++、有 python3 + pyserial 3.5（F18）。
  - 主机直连舵机的任何方案（含临时调试捷径）被否决（§00.7"主机直连舵机"作废条目）；单舵机实测也走"停官方控制器、在臂上原位、经 /dev/ttyS4"的路径（§00.6 第 7 条）。
  - 串口独占、固定周期、看门狗、软急停（Q10、Q11）等安全设计全部落在臂载控制器内（§4.1 ①层），其代码进本仓库 `arm_onboard/`。
  - 回滚依赖 `arm_onboard/as_deployed/` 的原厂二进制备份（F7、F17，§6.4 第 3 条）。
- 何时重新审视：若臂载计算机算力或非 RT 内核被实测证明无法支撑控制频率目标（P1.2 后仍达不到），或机器狗部署计划取消/变更，重开新 ADR。
